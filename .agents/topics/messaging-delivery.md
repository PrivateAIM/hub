# Messaging Delivery Semantics

Read before changing retry, ordering, redelivery, process-status locking, the analysis reconciler or bucket reply correlation.

## Messaging delivery semantics

Messaging delivery semantics (#1935, #1947) — Implemented. Fixes only the defects that have local fixes; the topology/orchestration findings stay open. What is not obvious from the diff:

- **A WORK message gets more than one attempt.** An AMQP driver that acks and skips every `redelivered` message means a handler throw (nack + requeue) or a worker crash mid-build loses the command silently. A failure or redelivery re-publishes with `metadata.attempt + 1` and exponential backoff (`maxAttempts` 5, `retryDelay` 1s, capped at 30s), then drops with an error log. Deliberately no dead-letter queue yet. A redelivery is NOT always a dead consumer: a channel reset (reconnect) redelivers a message whose handler is still running in a live process, so the driver tracks in-flight ids and skips such a copy. That guard is per process only — a redelivery landing on ANOTHER replica (connection drop, `consumer_timeout`) still runs a second time until a distributed claim exists (F9/F10). Operator consequence: RabbitMQ's `consumer_timeout` must exceed the longest build — documented in [deployment configuration](../../docs/src/guide/deployment/configuration.md#message-delivery-rabbitmq).
- **`context.handle` neither awaited nor returned the child handle**, so every `await context.handle(EVENT)` resolved immediately: a command was acked before its result event was published, and a publish error became an unhandled rejection. It now returns the promise, so awaited publish failures reach the handler's `catch` (and the driver's retry). Not covered: the `EXECUTION_PROGRESS` callbacks run by docken's `waitForStream`, which invokes `onBuilding`/`onPushing` fire-and-forget — a failed progress publish there was and still is an unhandled rejection, and those publishes are not ordered against `EXECUTION_FINISHED`.
- **All consumers run at `prefetchCount: 1`, events included.** Aggregator handlers read-modify-write the entity, and typeorm's `save()` diffs against the database, so a concurrently handled `PROGRESS` wrote `STARTED` back over `EXECUTED`. Serialization holds per replica only. Across replicas, `isProcessStatusTerminal` (`core/services/helpers.ts`) makes `STARTED`/`PROGRESS` no-ops once a process is terminal; only the command path (`STARTING`) leaves a terminal status. `MasterImageService` BUILD now saves `STARTING` **before** dispatching, for the same reason.
- Failure payloads typed `error: Error` serialized to `{}`: `serializeMessageBusPayload` (server-kit; now hubwire's `serializeMessage`) keeps `name`/`message`/`code` on the wire. A failed master-image build emitted `EXECUTION_FINISHED` — it now rethrows into `EXECUTION_FAILED`. The synchronizer's `'*'` telemetry handler was shadowed for `EXECUTION_FINISHED` (a specific handler wins), so that handler now records the event itself. `'*'` stays a fallback, not a tap. The AMQP driver and `RegistryProjectLinkHandler` now receive a logger, and a dispatch that no consumer accepts (memory driver) logs a warning — the AMQP driver's `publish()` now resolves `true` once confirmed, since amqplib's boolean only reports write-buffer backpressure. Retrying WORK queues include the shared telemetry log queue, where the backoff holds the single prefetch slot; the log writer therefore drops a line that fails validation **or that the log store rejects** (a VictoriaLogs outage) instead of letting it be retried — a retry would hold the slot through its backoff and pile every service's log lines up in the broker.

**F4 landed on amqp-extension 5**: the six reply routings (worker builder/distributor/master-image events, storage bucket/bucket-file events) are WORK queues with `ordered: true`, which the AMQP driver declares as `x-single-active-consumer` on **both** publish and consume (the broker answers differing arguments with 406). Ordering is load-bearing, not cosmetic: plain competing consumers would let a stale `PROGRESS` save overwrite `EXECUTED` on another replica. An ordered redelivery whose original still runs in-process is held until the original settles rather than acked, since acking frees the prefetch slot and lets the next message of the stream run beside it. A retry re-publishes to the queue tail, so a retried event can land after a later one — `isProcessStatusTerminal` absorbs that for status events. Rollout: worker and storage before server-core. v5 declares every default-exchange queue with `x-queue-type: classic`; verified against RabbitMQ 4 that this re-declares v4's argument-less queues in both directions without a 406.

**Race-safe status transitions (F9, #1937).** Every process-status transition — analysis build/distribution start, configuration lock/unlock, master-image BUILD and its dispatch-failure rollback, and the three worker aggregators — runs read-check-mutate-save on a row held by `SELECT … FOR UPDATE`, via `updateLockedEntity` (`adapters/database/locked-update.ts`), exposed to `core/` as `IAnalysisRepository` / `IMasterImageRepository` `.updateLocked(id, fn)`. So `canStart` and `isProcessStatusTerminal` are evaluated on the row as it is now: of concurrent starts exactly one dispatches, and a late event cannot write an older status back. Every other writer of those rows goes through the lock too, or a stale copy is written back (`save()` diffs against the database): the three metadata recalculators apply only their derived fields to the locked row (`saveAnalysisPatch`), `AnalysisService.update` (a user PATCH, which awaits a permission evaluation between its read and its write) and the master-image synchronizer `Object.assign` their fields into it. Not `repository.merge()` inside the callback: typeorm's mutates, the test fake's returns a copy, so the port does not promise either. Deliberately **not** `repository.update()` — it bypasses the subscribers that publish the realtime + audit events. The callback is synchronous (nothing awaited under the lock); dispatch happens after commit. A master-image BUILD claims `STARTING` only from a non-`STARTING` row (400 otherwise), so its dispatch-failure rollback, which reverts only a row still `STARTING`, can only undo its own claim. A `STARTING` older than 15 min is presumed dead and may be taken over — master images have no check command, so this stays their only escape — the reconciler (F14) covers analyses only. A CHECK_FINISHED verdict carries `checkedAt` (the snapshot's `updatedAt`) and is dropped when the locked row is newer; a verdict without it (older worker) applies as before. Any write bumps `updatedAt` — a node-progress recalc included — so a verdict that raced an unrelated write is dropped as well, silently; re-run the check. better-sqlite3 runs unlocked and is **not** race safe (no row locks; its one shared runner nests concurrent transactions as savepoints) — no worse than the plain `save()` it replaced. Covered by `test/unit/adapters/database/status-transition-lock.spec.ts` (concurrent starts, and a late `EXECUTION_PROGRESS` read while `EXECUTED` commits for each of the three aggregators), negative-controlled on postgres and mysql. Not done: run ids to drop a previous run's late `EXECUTION_FINISHED` after a new `STARTING`. The aggregators do not touch the `DataSource`: the status rules moved into core (`applyEvent` on `AnalysisBuilder` / `AnalysisDistributor` / `MasterImageBuilderService`), the storage-bucket and authup handlers go through the repository ports, and `updateLockedEntity` is called only by the repository adapters — an authup user deletion now detaches analyses via `updateLocked` instead of a full-copy save.

**TaskManager removed (F10/F11).** Its only job was correlating storage bucket replies, and the reply already names its analysis bucket: `CREATION_FINISHED` is linked by `refType: 'analysis'` + `refId` + `parseAnalysisBucketName(name)` (core-kit, the inverse of `buildAnalysisBucketName`), and a reply that does not resolve to one is ignored. Trusting the reply rests on storage forwarding `CREATION_FINISHED` to the bus only for core's own (bus) creates, never for HTTP-created buckets; as defence in depth a bucket whose `realmId` differs from the analysis's is never linked. A reply for an `(analysisId, type)` already linked to a different bucket — a repeated `check()` sent a second create — dispatches a storage delete for that new orphan bucket, never for the linked one; the ordered reply queue (F4) makes this check-then-link race-free without a lock. `DELETION_FINISHED` matches by bucket id only, as before. `CREATION_FAILED` is now consumed and logged against the analysis — storage echoes the command's optional `refType`/`refId`/`name` on it, and without them (older storage) the error is logged without refs; nothing is persisted and the F14 reconciler does **not** re-provision it — a missing bucket still needs a `storageCheck` (open). **Breaking:** `TaskManager` (and its types) is removed from `@privateaim/server-kit`; `IBucketCaller` takes no metadata. **Rollout:** stop old server-core replicas before new ones serve traffic — an old replica holding the `storageBucketEvents` slot drops `CREATION_FINISHED` for a create a new replica sent (no task entry), leaving that analysis bucket-less until a `storageCheck` command; the reverse direction links fine. See [deployment configuration](../../docs/src/guide/deployment/configuration.md#message-delivery-rabbitmq).

**Reconciler + staleness in core (F13/F14).** The 15-min stale verdict moved from the worker check handlers into core: a worker now reports an in-progress (`STARTING`/`STARTED`) process as-is, and `applyEvent` CHECK_FINISHED turns that into `FAILED` when the locked row's `updatedAt` is older than `ANALYSIS_PROCESS_STALE_THRESHOLD_MS` (`core/services/helpers.ts`). `AnalysisReconciler` (`core/services/analysis-reconciler/`) runs from a `ComponentsModule` background component (`app/components/analysis-reconciler/`, node-client shape: a pass at start, then every 5 min) and dispatches the existing build/distribution check for every in-progress row older than the threshold (`IAnalysisRepository.findManyInProgressUpdatedBefore`, a `Raw` bound `Date` — the timestamp-filter trap). No lock: per replica, duplicate verdicts are dropped by `isCheckVerdictStale`. So a long single step is not judged stale, the builder/distributor execute handlers send a heartbeat `EXECUTION_PROGRESS` (last percent) every 5 min, and core's PROGRESS branch stamps `updatedAt` explicitly when the percent is unchanged (typeorm writes an explicit update-date value instead of `CURRENT_TIMESTAMP`; pinned on postgres/mysql/sqlite by `test/unit/adapters/database/process-staleness.spec.ts`, negative-controlled) — throttled to once per `ANALYSIS_PROCESS_HEARTBEAT_STAMP_MS` (1 min), otherwise the event is a no-op with no save. The heartbeat goes quiet after 2 h without real progress, so a hung docker stream goes stale — but stale is not recovered by itself: with one worker the CHECK waits behind the hung EXECUTE on the same prefetch-1 queue, so it takes a worker restart, a second worker replica, or RabbitMQ's `consumer_timeout`. EXECUTION_STARTED / PROGRESS / FAILED / FINISHED apply only to a STARTING/STARTED row (FINISHED since #1960, the other three since the post-beta.70 audit — before, a late STARTED from a retried EXECUTE turned an analysis unlocked to `null` into STARTED and left it unlockable, unstartable and uncheckable), so a late event cannot resurrect a run core already declared FAILED (a stale verdict during a worker outage, with the retried EXECUTE re-published behind the reconciler's CHECKs) or reset to null; run ids are the full fix. The distributor check reports an in-progress distribution with a permanently missing precondition (no nodes, no registry, no registry project) as still in progress, like a missing image, so the stale rule can fail it. Ceilings: a CHECK per stuck row per replica per 5 min with no TTL — they pile up while no worker consumes; master images and failed storage buckets are not reconciled. **Rollout: workers before server-core** — an old worker still applies its own 15-min rule and sends no heartbeat, so the new reconciler's automatic check would fail its healthy long builds.

**Cache removal, F12, F6, F17, F18.**
- **Cache module removed:** nothing has read it since `TaskManager` went. **Breaking:** `Cache`, `CacheModule`, `CacheInjectionKey`, the adapters and `withCache()` are gone from `@privateaim/server-kit`.
- **F12, bucket uniqueness:**
  - core `analysis_buckets` is unique on `(analysisId, type)`. The migration keeps the oldest link per key and deletes the rest (their file mirror rows cascade; the storage bucket stays as an orphan).
  - storage `buckets` is unique on `(refType, refId, name)`; NULL refs are unconstrained. The migration detaches newer duplicates (refs set to NULL) and deletes nothing.
  - Storage's create handler replies with the existing bucket for the same ref + name + realm, and resolves a lost unique race to the winner.
  - Because that shared ref namespace could be hijacked, **`POST /buckets` answers 400 for a `refId`**: storage cannot verify who owns the referenced resource, so only the owning service sets refs, over the bus.
- **F6, transient failures:** a worker handler rethrows a transient error so the bus retries it with backoff. Transient means a hapic network error or 5xx/429, dockerode `statusCode >= 500`, or a socket error code. On the last attempt (`metadata.attempt` vs the new `MESSAGE_BUS_MAX_ATTEMPTS` export) it reports `*_FAILED` instead, so nothing is dropped silently. Errors inside a docker build/push stream (`errorDetail`) still count as permanent.
- **F17, registry dispatch:** `RegistryComponentCaller` only dispatches to `registryCommands` when a bus exists, and calls the component directly only without one.
  - Consequence: a node's robot credentials are set shortly after the request returns.
  - `registryCommands` is unordered, so a rename sends one `PROJECT_RELINK` (carrying the old `externalName`) instead of unlink + link.
  - Harbor errors are still caught and logged by the link/unlink handlers, so they are not retried.
- **F18, dead routings:** `telemetryEventEvents`, `telemetryLogEvents` and `registryEvents` had no subscriber and are removed. **Breaking:** `EventEventMessageBusRouting` and `LogEventMessageBusRouting` are gone from `@privateaim/server-telemetry-kit`. `storageBucketFileTasks` is kept (core publishes bucket-file deletes to it).
- **Bucket actor (pre-existing bug, found while doing F12):** `BucketValidator` dropped `actorId`/`actorType`, so every bucket was stored without a creator and `isOwnedByActor` never matched. The create handler now records the actor of a trusted sender: the HTTP identity (which overrides anything in the body) or the bus payload. Buckets created before this fix keep a null actor and are not backfilled. Because the registry credentials (F17) now arrive shortly after the request, `FNodeRegistryCredentials` re-reads them up to 3 times until the secret appears. Uploads to a bucket without a `refId` now require ownership or `BUCKET_UPDATE` with realm access (`BucketService.checkUploadAccess`, 403 before anything is stored; previously any logged-in user could upload into any bucket); analysis buckets older than the ref columns got their ref back from their name in `1788900000000-BackfillAnalysisBucketRefs` (both dialects), since without it node and analysis uploads into them answered 403; ref'd buckets keep server-core's after-the-fact check until capability tokens land.

Still open: the authup aggregator on redis pub/sub (F20), run ids, a message TTL for the reconciler's CHECK backlog, and master-image reconciling.
