# Messaging and Components

Read before changing the message bus wiring, a dispatcher, a worker, an aggregator, a scheduled component or a process-status transition.

## Domain Events & Messaging

TypeORM subscribers in `adapters/database/subscribers/` (grouped by domain: `analysis/`, `node/`, `project/`, `registry/`, `master-image/`) publish domain events via the entity event system. Events flow through Redis pub/sub and AMQP (RabbitMQ).

AMQP consumers are wired via two DI modules:
- **AggregatorsModule** (`app/modules/aggregators/`) — Starts AMQP event consumers that react to events from other services (builder, distributor, storage, master-image, authup). Aggregators depend only on core services and repository ports (resolved from `AnalysisInjectionKey` / `DatabaseInjectionKey`), never on a `DataSource`: the worker status rules (event → status transition, `isProcessStatusTerminal`, `isCheckVerdictStale`) live in core as `AnalysisBuilder.applyEvent` / `AnalysisDistributor.applyEvent` / `MasterImageBuilderService.applyEvent`, while the storage-bucket and authup handlers keep their orchestration in app over the ports. Storage-bucket replies are correlated by the bucket itself (`refType`/`refId` + `parseAnalysisBucketName(name)`), not by a task store.
- **ComponentsModule** (`app/modules/components/`) — Registers `RegistryComponentDispatcher` in the container: with a message bus it only dispatches to the `registryCommands` queue through a `RemoteDispatcher` (the registry consumer runs it; a throwing command is retried, but the Harbor handlers log and swallow Harbor errors), and calls the component in-process through a `LocalDispatcher` only when there is no bus. A work queue keeps a command until a consumer takes it — the memory driver too — so a command dispatched before the registry consumer subscribed is not lost. Starts task consumer workers (registry) and the background components: node-client permission sync and the analysis reconciler (depends on `analysis` for the builder/distributor). Both modules start their components fire-and-forget; `teardown()` `stop()`s each (a `RemoteWorker`'s `stop()` waits for its own start, the authup aggregator listens before it subscribes), then awaits `settled?.()` on each (a scheduled component's covers the first pass).

**The bus is hubwire's `MessageBus`.** server-kit's `MessageBusModule` always registers one,
typed `IMessageBus`, under `MessageBusInjectionKey`: with `@hubwire/amqp`'s `AmqpMessageBusDriver`
(topic exchange `MESSAGE_BUS_TOPIC_EXCHANGE` = `FLAME`) when a RabbitMQ connection string is
configured, else the in-process `MemoryMessageBusDriver`; its `teardown()` closes the bus
(`IMessageBus.close()`, which closes the driver). Every driver keeps one delivery contract:
`publish()` resolves once the transport took the message and never waits for (or sees) a
handler, a WORK message waits in its queue until a consumer takes it, and a handler reads its
attempt from `metadata.delivery = { attempt, maxAttempts }`. Dispatchers and workers require a
bus, so every module that builds one declares the `messageBus` dependency and
`resolve`s it. A publisher whose only consumer is another service — the log transports and
entity-event handlers (server-telemetry consumes them; telemetry itself is the exception),
server-storage's bucket and file events, the worker's analysis log lines — resolves
`RemoteMessageBusInjectionKey` instead, which `MessageBusModule` registers only for a driver
other than the memory driver, and is not built without it: the memory driver would keep every
such message in the heap until `close()`. hubwire logs nothing itself: hub passes `hooks` built by server-kit's
`message-bus/hooks.ts` factories, and `silentRoutings` (server-telemetry-kit's
`TELEMETRY_SILENT_MESSAGE_BUS_ROUTINGS`) keeps the publish of a log line or audit event out of
the log. WORK routings are
retried by amqp-extension (counter in the `x-attempt` header, `MESSAGE_BUS_MAX_ATTEMPTS` = 5 attempts, exponential backoff
capped at 30s, then dropped) with an in-process redelivery guard; delivery is at-least-once.
Hub-specific policy stays in hub: the routings, `ordered` reply queues and the exchange name.

**Process-status transitions are row-locked.** Any read-check-mutate-save of a
`buildStatus`/`distributionStatus` (command starts, configuration lock/unlock, the master-image rollback,
the worker aggregators) goes through `updateLockedEntity` (`adapters/database/locked-update.ts`)
— `core/` reaches it as `IAnalysisRepository` / `IMasterImageRepository` `.updateLocked(id, fn)`.
It holds the row with `SELECT … FOR UPDATE` and saves through the transaction manager, so
subscribers still publish; never replace it with `repository.update()`. `fn` is synchronous
and returns `true` to save; dispatch to the worker only after it resolves. A CHECK_FINISHED
verdict whose `checkedAt` predates the locked row's `updatedAt` is dropped — any write
counts. Every other writer of these rows must not `save()` a copy read earlier either: the
recalculators apply their derived fields via `saveAnalysisPatch`; `AnalysisService.update` and
the master-image synchronizer `Object.assign` into the locked row.

**Stuck processes are judged and recovered by server-core** (F13/F14). The worker's
check reports an in-progress (STARTING/STARTED) build/distribution whose image is not there as
it is; `applyEvent` turns that verdict into FAILED when the locked row is older than
`ANALYSIS_PROCESS_STALE_THRESHOLD_MS` (15 min, `core/services/helpers.ts`). Running workers keep
the row fresh: an EXECUTION_PROGRESS that leaves the percent unchanged stamps `updatedAt`
explicitly once the row is older than `ANALYSIS_PROCESS_HEARTBEAT_STAMP_MS` (1 min) and is
otherwise a no-op (typeorm skips a no-op save, and a heartbeat repeats the last percent), and
the analysis builder/distributor execute handlers re-emit their last progress every 5 min —
until no real progress arrived for 2 h, so a hung docker stream goes stale. Stale is not
recovered: with one worker the CHECK waits behind the hung EXECUTE on the same prefetch-1 queue,
so recovery needs a worker restart, a second worker replica, or RabbitMQ's `consumer_timeout`.
Every EXECUTION_* event (STARTED, PROGRESS, FAILED, FINISHED) applies only while the locked row is STARTING/STARTED, so a late finish cannot
resurrect a run already FAILED or reset to null (full fix: run ids). The distributor check reports
an in-progress status for permanently missing preconditions (no nodes, no registry, no registry
project), so the stale rule fails such a run. `AnalysisReconciler.reconcile()`
(`core/services/analysis-reconciler/`) selects in-progress rows older than the threshold
(`IAnalysisRepository.findManyInProgressUpdatedBefore`, a `Raw` bound `Date` — the
timestamp-filter trap) and dispatches the existing check commands; the app component
(`app/components/analysis-reconciler/`) runs it at start and every 5 min on every replica,
without a lock — a duplicate verdict is dropped by `isCheckVerdictStale` (CHECKs carry no TTL, so
they queue up while no worker consumes). Rollout: workers before server-core — an old worker has no
heartbeat and judges staleness itself, so the reconciler's checks would fail its long builds. Master images are
out of scope: they have no check command, and BUILD takes over a 15-min-stale build itself.

Implementation classes live in `app/aggregators/` and `app/components/`.

## Shared Components

Shared Components — Implemented on `refactor/shared-components`. Components, callers and the message bus moved out of server-kit into [`hubwire`](https://github.com/tada5hi/hubwire) (a tada5hi monorepo shared with authup, now published as `hubwire` + `@hubwire/amqp`; at that time `synergos` + `@synergos/amqp` `^0.0.0`), and the AMQP retry/redelivery hardening of item 26 moved one level further down, into amqp-extension (5.1.1, transitive through `@hubwire/amqp`; hub declares no direct `amqp-extension` dependency any more). **The library API this item names is synergos 0.0 / 0.1's** (`ICaller`, `DirectCaller`, `DispatchCaller`, `WorkerCaller`, `onUndelivered`, body `metadata.attempt`); hubwire never exported it — item 35 replaced it with hubwire 0.2's dispatchers and workers (rename table there). What is not obvious from the diff:

- **Observability is hooks, not a logger.** hubwire takes no logger: every former log site is a typed `hooks` option, and a hook that throws is ignored by the library. server-kit's `message-bus/hooks.ts` is the one place hub turns them into log lines — `createMessageBusLogHooks(logger, { silentRoutings })` (publish/consume/unhandled at debug, a failing handler at error), `createAmqpDriverLogHooks` (retry and malformed at warn, drop at error), `createDispatchCallerLogHooks` (undelivered at warn; removed in item 35), `createWorkerCallerLogHooks` (a reply with no publish routing at warn; now `createRemoteWorkerLogHooks`) and `createScheduledComponentLogHooks(logger, name)` (a failed pass at warn). `MessageBusModule` wires the first two itself. Message ids ride as the `messageId` label, never in the text. The old `logging: false` publish option of the log and event callers is now `MessageBusModuleOptions.silentRoutings`: every service factory passes server-telemetry-kit's `TELEMETRY_SILENT_MESSAGE_BUS_ROUTINGS`, because a logged publish of a log line would feed the logger's own transport back into the bus. For the same reason `LogComponentCaller` and `EventComponentCaller` got no `onUndelivered` hooks: with synergos's memory driver every log publish outside telemetry was undelivered (dropped). The hook is gone since item 35, and a memory queue now keeps such a message, so outside telemetry they are built only over AMQP (item 35).
- **The bus is always there.** `MessageBusModule` registers an `IMessageBus` in every service — over AMQP when a RabbitMQ connection string is configured, else the in-process `MemoryMessageBusDriver` — and synergos's `DispatchCaller` / `WorkerCaller` required one. Every module that builds a caller declares `messageBus` as a dependency and `resolve`s it (only the lazy logger-transport `save` callbacks still `tryResolve`, since a line logged during boot can arrive before the bus is set up). Production behaviour is unchanged: every service factory already ran `withMessageBus()` and the module already fell back to the memory driver. What changed is the test apps (server-core, server-storage), which now register a memory bus instead of none — a command was published to it and reported undelivered rather than skipped by a caller without a bus (since item 35 it waits in the memory queue) — and that the entity-event `EventComponentCaller` and the worker's `LogComponentCaller` were always built rather than only when a bus resolved (item 35 builds them only over AMQP again). Nothing double-handles: the only routings a service both publishes and consumes in-process are server-core's `registryCommands` (intended, see F17 below) and telemetry's own event queue, whose entity events the `EntityEventHandler` skips (`refType === event`).

- **One contract for two things that were both called "component".** `IComponent { start, stop, status }` (hubwire) now covers the message-handler router (`Component`, formerly `BaseComponent`) and the scheduled background job (`defineScheduledComponent({ schedule, run, runOnStart?, hooks? })`). Every hand-written `task`/`stopped`/`lastSuccessAt`/`runningSince` block is gone: node-client sync and the analysis reconciler (server-core), the telemetry event cleaner, the messenger sweeper. A `run` that throws is logged and does not stamp `lastSuccessAt`; node-client and the reconciler throw after logging a partial failure (`failed > 0`) for that reason, and pass **no** hooks to the scheduled component so a failure is logged once, at error level (the cleaner and sweeper pass `createScheduledComponentLogHooks`, so theirs log at warn). `start()` never rejects.
- **Every `ComponentsModule` (+ server-core's `AggregatorsModule`) now stops what it started** in `teardown()`, and `MessageBusModule.teardown()` closes the driver. Before, a consumer had no `stop()` (the bus could not cancel one), the telemetry cleaner's cron task was never stopped, and the AMQP connection outlived the app. server-core starts its components fire-and-forget, so its teardown awaited those starts first — a synergos worker caller still starting would otherwise subscribe after its `stop()` (dropped in item 35: hubwire's `RemoteWorker.stop()` waits for a concurrent start). Ceiling: a scheduled component's `stop()` does not wait for a pass already running.
- **The telemetry cleaner is not a command.** `EventComponentCleanerHandler` became `createEventCleanerComponent` (`app/components/event-cleaner/`, `'0 1 * * *'` plus a pass at start). Its first pass does not run inside `Component.initialize()`, where a failure could reject boot; a failure is logged and boot continues. The messenger sweeper uses `runOnStart: false`, keeping "first sweep one interval after boot"; the unref'd `setInterval` is gone, so `teardown()` is what lets the process exit.
- **F17 — registry dispatch follows #1962** (the in-process fallback is gone since item 35). `RegistryComponentCaller` publishes each command to `registryCommands` itself (`buildMessage` + `IMessageBus.publish`, the same message a `DispatchCaller` builds) because synergos's `DispatchCaller.call()` did not report whether the bus accepted it. Accepted → done: the registry consumer on whichever replica takes it runs it, with the bus's retry. Not accepted (memory driver with no consumer yet) → `onUndelivered` (warn) and the command runs in-process through a `DirectCaller`; no bus → in-process. A failing direct call surfaces its own error and is not re-queued. The compound caller (in-process first, then the queue, every error swallowed) is gone and was not ported to hubwire. `registryCommands` is not `ordered`, so a registry-project rename sends one `PROJECT_RELINK` (carrying the old `externalName`) instead of an unlink and a link; an admin's separate `PROJECT_UNLINK` / `PROJECT_LINK` requests can still race (making the routing `ordered` would answer 406 until the existing queue is deleted).
- **F6's last-attempt detection needed synergos ≥ 0.1.0** (0.2 reads `metadata.delivery` instead, item 35). #1962's `isRetryableFailure` (`apps/server-core-worker/src/app/components/helpers.ts`) reads `metadata.attempt` and compares it with `MESSAGE_BUS_MAX_ATTEMPTS`, which `MessageBusModule` also passes as the AMQP driver's `maxAttempts`, so the two cannot diverge. With amqp-extension the counter travels only in the `x-attempt` header; `@synergos/amqp` 0.1.0 copied it into `metadata.attempt` on consume (tada5hi/hubwire#11) — never onto the wire. On 0.0.0 the attempt always read 1, so a transient failure was retried and then dropped instead of reported as `*_FAILED`.
- **Wire format is byte-identical except one field: the retry counter moved from the body (`metadata.attempt`) to the `x-attempt` AMQP header**, set by amqp-extension's `retry` consume option (`maxAttempts` 5, base delay 1s doubled per attempt, capped at 30s — unchanged). Exchange names (`FLAME` is now `MESSAGE_BUS_TOPIC_EXCHANGE` in server-kit), `type`/`messageId`/`persistent`, `x-single-active-consumer` on ordered routings and `prefetchCount: 1` are unchanged. **Mixed versions during a rollout retry more, never less, and never forever:** a missing or invalid header reads as attempt 1, an old driver re-publishes without headers (resetting the new side's count) but keeps counting in the body, which the new side never rewrites — so the old side's body counter still bounds a message that bounces between old and new replicas. No upgrade order is required for this; the item-26 orders (workers and storage before server-core) still hold. The in-process redelivery guard now lives in amqp-extension (per consumer, kept across reconnects; still per process — F9/F10 unchanged): a redelivered copy of a message whose handler still runs is held until the original settles, ordered or not, then acked — or requeued when the original's retry re-publish failed, since the original's nack went to the reset channel (hub's driver acked the copy and lost the message then). A retry logs a warning and an exhausted message an error naming its type and id; a crashed redelivery's retries are not logged (amqp-extension reports only its drop). A worker reply never carries the command's body `metadata.attempt`, so an old server-core does not drop it early.
- **Breaking for npm consumers of `@privateaim/server-kit`**, with **no** aliases: `BaseComponent`, the `Component` / `ComponentCaller` / `ComponentHandler*` / `ComponentMetadata` / `ComponentEventMap` types, `DirectComponentCaller`, `MessageBusDispatchComponentCaller`, `MessageBusWorkerComponentCaller`, `CompoundComponentCaller`, `ComponentError` / `isComponentError`, `MessageBus`, every `MessageBus*` routing/payload/driver type, `AmqpMessageBusDriver`, `MemoryMessageBusDriver`, `buildMessageBusPublishPayload`, `isMessageBusPayload`, `serializeMessageBusPayload` and the unused `Aggregator` type. They moved to `synergos` (`@synergos/amqp` for the AMQP driver; since item 35 `hubwire` / `@hubwire/amqp`, under that item's 0.2 names) under the renames `BaseComponent` → `Component`, `Component` → `IComponent`, `ComponentCaller` → `ICaller`, `DirectComponentCaller` → `DirectCaller`, `MessageBusDispatchComponentCaller` → `DispatchCaller`, `MessageBusWorkerComponentCaller` → `WorkerCaller`, `MessageBusPayload*` → `Message` / `MessageInput` / `MessageMetadata`, `MessageBusRouting(Type)` → `MessageRouting(Type)`, `MessageBusHandler(s)` → `MessageHandler(s)`, `buildMessageBusPublishPayload` → `buildMessage`, `isMessageBusPayload` → `isMessage`, `serializeMessageBusPayload` → `serializeMessage`; a bus catch-all handler is keyed `'*'`. server-kit keeps `MessageBusModule` (+ `MessageBusModuleOptions`, now with `silentRoutings`), `MessageBusInjectionKey` (now `TypedToken<IMessageBus>`), `MESSAGE_BUS_TOPIC_EXCHANGE` and the log-hook factories above; server-telemetry-kit adds `TELEMETRY_SILENT_MESSAGE_BUS_ROUTINGS`, and every hub caller subclass now requires `messageBus` in its options. `ComponentError` moved into the worker (`apps/server-core-worker/src/app/components/error.ts`), its only user. **`@privateaim/server-telemetry-kit`** dropped `EventCommand.CLEAN`, `callClean` and the `CLEAN` event-map entry. The three domain kits (`server-core-worker-kit`, `server-storage-kit`, `server-telemetry-kit`) extend the library's `Component`, so their consumers need it installed (`hubwire` since item 35); it is a plain dependency of all three — server-storage-kit and server-telemetry-kit could move it to peer + dev, like their server-kit dependency.

## hubwire 0.2 migration

hubwire 0.2 migration — Implemented. The 0.1 imports (the library's former package name) became `hubwire@^0.2.1` / `@hubwire/amqp@^0.2.1` (`@hubwire/test@^0.1.1` as a dev dependency of server-kit and server-core); callers became dispatchers and workers: `DispatchCaller` → `RemoteDispatcher`, `DirectCaller` → `LocalDispatcher` (`callAndWait` → `dispatch(...).replies`, `callWith` → `component.handle(..., { handle })`), `WorkerCaller` → `RemoteWorker` (`consumeRouting` / `publishRouting` → `consume` / `publish`). What is not obvious from the diff:
- **Breaking for npm consumers of the kits.** The hub caller subclasses extend `RemoteDispatcher` and are renamed `*Caller` → `*Dispatcher` with `call*` → `dispatch*` methods, no aliases (`AnalysisBuilderComponentCaller` → `AnalysisBuilderComponentDispatcher` with `dispatchExecute` / `dispatchCheck`, `BucketComponentDispatcher`, `BucketFileTaskDispatcher`, `BucketFileEventDispatcher`, `LogComponentDispatcher.dispatchWrite`, `EventComponentDispatcher.dispatchCreate`, `MasterImage*ComponentDispatcher`, …): their options lost `hooks`, and the inherited `call()` is now `dispatch()`. server-telemetry-kit's `EntityEventHandler` context key `eventComponentCaller` → `eventComponentDispatcher`, its port `IEventPublisher.callCreate` → `dispatchCreate`. Inside the apps the same rename covers `RegistryComponentDispatcher` (`IRegistryDispatcher.dispatch()`, token `ComponentsInjectionKey.RegistryComponentDispatcher`), the service ports (`IAnalysisBuilderDispatcher`, `IBucketDispatcher`, …, ctx key `dispatcher`), server-storage's `http/dispatchers/` adapters and the spec fakes. server-kit dropped `createDispatchCallerLogHooks` and renamed `createWorkerCallerLogHooks` → `createRemoteWorkerLogHooks` (its `onUnrouted` takes one event object).
- **`publish()` does not report delivery.** It resolves `void` once the transport took the message, and a WORK queue keeps a message until a consumer takes it — the memory driver too. So `RegistryComponentDispatcher`'s (formerly `RegistryComponentCaller`) "accepted nowhere → run in-process" fallback (F17) is gone: with a bus it only dispatches (`RemoteDispatcher`), without one it runs the component through a `LocalDispatcher`. A command dispatched before the registry consumer started now waits in the queue instead of running inside the request.
- **The last attempt comes from the driver.** `isRetryableFailure` reads `metadata.delivery = { attempt, maxAttempts }` instead of comparing `metadata.attempt` with `MESSAGE_BUS_MAX_ATTEMPTS`; `MessageBusModule` still passes that constant as the AMQP driver's `maxAttempts`. Without a delivery (an in-process call) or on the memory driver (`1/1`) nothing retries, so a transient failure is reported as `*_FAILED` instead of rethrown into a drop.
- **Shutdown waits for a scheduled pass.** `stop()` never waits for a cron pass in flight; server-core's `ComponentsModule`, telemetry's `ComponentsModule` and messenger's `SweeperModule` now `stop()` every component, then await `settled?.()` on each (hubwire 0.2.1: optional on `IComponent`, required on `IScheduledComponent`), so a pass cannot outlive the database; scheduled components share the one `IComponent[]` with the workers. `MessageBusModule.teardown()` closes the bus (`IMessageBus.close()`) rather than the driver.
- **Cross-service publishes need AMQP.** A memory WORK queue keeps every message until a consumer takes it (0.1 dropped it), and without `AMQP_URL` no service but telemetry consumes the log and entity-event queues — so every log line and entity event would stay in the heap until `close()`. `MessageBusModule` therefore also registers the bus as `RemoteMessageBusInjectionKey`, only when the driver is not the memory driver, and the publishers whose consumer is another service resolve that token and are not built without it: the factories' log transport `save` and `EntityEventHandler` (server-core, server-storage; server-telemetry consumes its own), server-core-worker's analysis log lines, server-storage's bucket and file events to server-core. Covered by server-kit's `message-bus-module.spec.ts`. Ceiling: server-core's commands to the worker and to storage (build, distribute, bucket and file tasks) still use the always-registered bus, so without AMQP a triggered command waits in the memory queue until shutdown.
- **No start/teardown handshake.** server-core's `ComponentsModule` and `AggregatorsModule` start fire-and-forget and `teardown()` only `stop()`s (then `settled?.()`): a `RemoteWorker.stop()` waits for its own start and leaves no consumer, `settled()` covers a scheduled component's first pass, and the authup aggregator attaches its listener before it subscribes, so a `stop()` mid-start removes it.
- **Tests wait for handlers, not for `publish()`.** Bus-backed specs `drain()` (`@hubwire/test`) before asserting; the hooks spec asserts a failing handler through `onError` instead of a rejected publish; the storage-bucket-file spec's never-delivering bus is `FakeMessageBus`.
