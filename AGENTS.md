# FLAME Hub — Agent Guide

FLAME Hub is a monorepo for the central services of the FLAME platform — a privacy-preserving analytics infrastructure. It contains backend services (core API, storage, telemetry, messenger, worker), a Nuxt frontend, shared libraries, and a VitePress documentation site. All packages are TypeScript, built with tsdown (libraries) or tsdown + tsc (services), orchestrated by Nx.

## Quick Reference

```bash
# Setup
npm ci

# Development
npm run build                   # Build all packages (Nx)
npm run test                    # Test all packages (Nx + Vitest)
npm run lint                    # ESLint across all packages
npm run lint:fix                # ESLint with auto-fix

# Dev servers
npm run dev --workspace=apps/client-ui          # Nuxt frontend
npm run dev --workspace=apps/server-core        # Core API server
npm run dev --workspace=apps/server-messenger   # Realtime/WebSocket server
npm run dev --workspace=apps/server-core-worker # Worker service
npm run dev --workspace=docs                    # Documentation site
```

- **Node.js**: 24
- **Package manager**: npm (workspaces)
- **Build orchestration**: Nx 22

### Workspace Layout

Applications (services + frontend) are in `apps/`, shared libraries are in `packages/`, and documentation is in `docs/`. Libraries export ESM (`dist/index.mjs` + types), services compile with tsdown + tsc.

## Documentation

The `docs/` directory contains a VitePress documentation site. When making changes that affect user-facing behavior, configuration, APIs, or service architecture, **update the corresponding docs pages**. The docs site is the authoritative reference for Hub — docs.privateaim.net should link here, not the other way around.

Key docs areas to keep in sync:
- `docs/src/reference/<service>/` — per-service pages (env vars, endpoints, usage)
- `docs/src/reference/<service>/<kit>.md` — per-package pages (install, API, usage)
- `docs/src/guide/user/` — user-facing workflows (projects, analyses, approval)
- `docs/src/guide/deployment/` — deployment configuration and guides

When you need additional context beyond what's in the code (e.g., deployment patterns, admin workflows, env var semantics), check the docs first: `docs/src/`.

Docs updated in `docs/src/guide/development/api.md` and `docs/src/reference/{core/core-http-kit,storage/storage-kit}.md`.

SSR hydration handoff (#1805) — Implemented (what the server render fetched now reaches the browser instead of being discarded). client-ui runs `ssr: true`, but every detail page fetched its record **twice**, and a list's initial load ran in a detached microtask that resolved *after* the HTML was flushed — the server paid for the request and shipped an empty list anyway. The seam is `@authup/client-web-kit`'s hydration store, provided by `@authup/client-web-nuxt`'s kit plugin over `nuxtApp.payload.data` (both already dependencies at beta.63 — **no authup bump**). Hub adds **no install option and no plugin**: `createListRaw` calls `injectHydrationStore()` and no-ops when it returns `undefined`, so a host without one skips the server-side load entirely rather than rendering rows the hydrating client cannot reproduce. Four things in it are not obvious:

    - **The list key is `flame:list:<type>:${useId()}`, never the query.** A query-derived key has to be re-derived *identically* on the client, which makes filter insertion order, a `query` prop assembled from store state that is not populated yet on one side, and two same-query lists on one page all load-bearing — and each of those fails **silently**, as a list that simply fetches twice again. Vue 3.5's `useId` is stable per component-tree position across the boundary, so agreement is structural rather than something a caller can get wrong. The entity type is in the key only to bound the blast radius of an entry that is recorded but never adopted.
    - **`onServerPrefetch` is registered on BOTH sides, and that is load-bearing.** A non-empty `instance.sp` is what makes Vue call `markAsyncBoundary()` after setup, giving the component's subtree a fresh `useId` counter; `instance.sp` is read in exactly two places (`runtime-core`'s boundary check and `@vue/server-renderer`, the only invoker). Registering the hook only under `isServerRuntime()` marks the boundary only on the server, so every `useId()` inside or after a list shifts between renders — a second same-type list then derives the key the server used for the FIRST one and adopts the wrong rows, with its own load suppressed so it never corrects. `list-hydration.spec.ts`'s two-list round trip is the negative control; it fails the moment the registration is moved back inside the server branch.
    - **The composed `query` travels in the snapshot.** `query` is assigned nowhere but inside `load()`, which the adopting client skips, and the socket handler reads its sorts to decide whether a realtime-created entity belongs at the top of a full first page. Without it, realtime inserts stop silently on every hydrated list (a ≥10-row list on `/projects`, `/projects/in`, `/admin/nodes`, …) until the user pages or searches.
    - **A collection query must not request a permission-gated column any more.** The list's rows now reach the payload, i.e. the served HTML document. `fields: ['+accountSecret']` was dropped from the registry-projects list: nothing there rendered it (the details modal re-resolves by id with its own `+accountSecret`), so it was pure over-fetch that would have put every Harbor robot secret into the document.
    - **Only a load that ran to completion may be recorded.** An adopted snapshot *suppresses* the client's own load, so recording what a failed — or coalesced-away — load left behind strands the list on it with no retry. The `loaded` flag set at the end of `load()`'s try block is the enforcement point: `onServerPrefetch` awaits `load()` in a try/catch and records nothing unless it is set. `onServerPrefetch` is also what makes the renderer **wait**, which puts a list's upstream latency on the SSR critical path — the nine `[id].vue` detail pages already blocked SSR by awaiting in `setup()`, so this is not a new class of dependency.
    - **`useAsyncData` needs `deep: true`.** Nuxt 4 returns a `shallowRef`, and every one of the nine pages mutates its entity **per property** (`updateObjectProperties` does `src.value[key] = …`, or `extendObject`), so without it the page silently stops updating after a save. `useEntityRecord` centralises it. A second Nuxt trap sits next to it: 4.5.2's `asyncData.js` **defers** `initialFetch` to `onBeforeMount` during hydration when the payload holds no entry for the key, so `await useAsyncData(...)` can resolve with `data.value === undefined` **and** `error.value === null` — a guard of the form `if (error.value || !data.value) redirect` therefore bounces a page that is merely late.
    - **No authenticated route may get an `swr` or `isr` route rule** — the payload is per-request, and a cached one would be served to the wrong session. `apps/client-ui/nuxt.config.ts` declares exactly one route rule, `'/login/callback': { ssr: false }`.

    One consequence is accepted rather than fixed: list rows now render on the server, which puts `<VCTimeago>` on both sides of the boundary for the first time. It computes a relative string during `setup()`, so a bucket crossing between render and hydration — or clock skew — is a text mismatch, and Vue `console.error`s those in production builds too. Vue repairs the text; the cost is console noise on list pages and one more thing to rule out when debugging a real mismatch. The fix belongs upstream in `@vuecs/timeago` (SSR-stable first render, relative string in `onMounted`).

    Deliberately **not** done: records resolved by `createEntityManager` (a separate producer, tracked as a follow-up issue) and the pages that `await getMany` rather than a record (`pages/projects/[id].vue`, `pages/projects/index/in.vue`, `pages/admin/services/registry/index/client.vue`). Documented in [reference/frontend](docs/src/reference/frontend/index.md#server-rendering-and-hydration).

24. Indexed query surface + schema drift gate (#1842, #1823) — Implemented. All 15 rapiq entity schemas (12 server-core, 2 server-storage, 1 server-telemetry) declare `indexes` and opt into the indexed policies, backed by real DDL, and a typeorm-extension drift gate joins the migration CI for all four server apps. What is not obvious from the diff:

    - **`indexes` declares the QUERY SURFACE, not the table.** Every sequence is property-name-spelled and a leftmost prefix of a real PK/unique/`@Index`; entity indexes whose leading column is not queryable (nodes' `(externalName, registryId)` unique, events' `(expiring, expiresAt)` sweep index) are deliberately not declared. See [conventions.md](.agents/conventions.md#column-naming).
    - **Backing DDL**: 58 single-column indexes in server-core (`1788410000000-QueryIndexes`, both dialects), 13 in server-storage (`1788420000000-QueryIndexes`), and one `events(created_at)` index in server-telemetry, folded into the still-unreleased `1788220800000-EventWidenIpAddressAndRebuildIndexes` as the window's consolidation step (it briefly existed as its own `1788430000000-EventCreatedAtIndex`; anyone who executed a pre-fold file must drop their dev DB or fix its `migrations` table by hand). Eight server-core indexes land on FK columns whose implicit InnoDB index the new explicit index displaces (InnoDB silently drops the implicit one on creation, so a plain `DROP INDEX` in `down()` would fail with "needed in a foreign key constraint", non-transactionally). The mysql `down()` therefore RENAMES those eight back to the constraint's own name (`ALTER TABLE … RENAME INDEX` — metadata-only, legal while the constraint is live) instead of dropping them: the foreign key is never dropped, so there is no orphan window and nothing is re-added unvalidated. An earlier drop/re-add design under `SET FOREIGN_KEY_CHECKS=0` was replaced for exactly that reason — a checks-off `ADD FOREIGN KEY` does not validate existing rows, so any row orphaned by writes while the constraints were absent would sit permanently behind a constraint the database reports as satisfied.
    - **Postgres migrations commit per migration** (`migrationsTransactionMode: 'each'` in server-db-kit's `DataSourceOptionsBuilder`): under the previous `'all'`, every pending migration fused into ONE postgres transaction, so AlignAnalysesConstraintNames' ACCESS EXCLUSIVE lock on `analyses` (taken by its first `RENAME CONSTRAINT`) would have been held across QueryIndexes' entire 58-index build — blocking reads on the busiest table for the whole window at pod boot, for a duration scaling with the operator's data. `'each'` keeps every postgres migration atomic on its own and releases each migration's locks at its own commit; MySQL auto-commits DDL statement by statement regardless, so `'all'` never bought it anything.
    - **Write-cost trade-off, accepted and recorded**: the invariant forces an index onto every allow-listed key, so some indexes land on low-cardinality or write-hot columns no known query uses (`analyses.configuration_locked`, `analysis_bucket_files.root`, the storage tables' two `actor_type` columns). Accepted over another round of breaking allow-list narrowing; narrowing those allow-lists — and dropping the indexes with them — remains open as a follow-up.
    - **Telemetry event filters NARROWED** — `createdAt`/`updatedAt` removed — and that is a fix, not collateral: both are datetime columns behind `dateToISOStringTransformer`, and transformers apply on read, never to WHERE binds, so such filters compared an ISO string against the driver's native storage format and matched wrong rows *silently*. An expression-dialect filter on them now 400s; the bracket form drops silently. This deliberately diverges from authup, whose event schema keeps `createdAt` filterable despite the same TIMESTAMP+transformer shape — checked: there is **no** storage difference excusing it, so the divergence reads as an authup-side exposure to the same trap, not a hub-side quirk. Event sorts narrowed to `createdAt` only: events are append-only since #1866, so `updatedAt` always equals `createdAt` — a redundant ordering. `expiresAt` is excluded for a different reason: it is not `createdAt` plus a fixed window in general (an explicit publisher `expiresAt`, or `expiring: false`, wins over the auto-stamped default, and `EVENT_RETENTION_DAYS=0` disables the window entirely — see item 21 above), and no declared `indexes` sequence leads it, so allow-listing it would fail the parity spec's leading-key invariant. `sorts.default: { createdAt: 'DESC' }` is the soft-failure floor: sorts fail SOFT, so a dropped or no-longer-allowed sort parameter now degrades to newest-first (the admin events page's order) instead of to no ordering at all.
    - **The masterImage sorts allow-list was WIDENED, and that fixes a real bug**: the schema declared only `sorts: { default: { path: 'ASC' } }`, so the derived allow-list was `['path']` and the `virtualPath` sort client-vue's FMasterImages has been requesting was silently dropped all along — now explicit (`['name', 'path', 'virtualPath', 'createdAt', 'updatedAt']`). masterImageGroup, which declared no sorts at all (under `strict`, every requested key rejected), got the same explicit list. In the other direction, `analysis` filters lost `description`: a `text` column, unindexable under MySQL utf8mb4's 3072-byte key bound, and nothing in client-vue/client-ui ever filtered on it.
    - **#1823 root cause: a `RENAME TABLE` carries every constraint name over, but typeorm hashes them from table + column names.** Two renames (`analysis_entity` → `analysis` → `analyses`) left seven stale hashes, so every `migration generate` opened with spurious drop/recreates. `1788400000000-AlignAnalysesConstraintNames` (both dialects) renames them: 4 indexes via `RENAME INDEX` (MySQL) / `ALTER INDEX … RENAME` (postgres); the 3 FKs via drop+re-add on MySQL (no `RENAME CONSTRAINT` there), wrapped in `SET FOREIGN_KEY_CHECKS=0` with a `finally` restore — the setting is per-session and the connection returns to the pool on failure. Postgres renames the FKs directly. The rule is now in conventions.md: a table rename must re-derive every constraint name, or let `migration generate` write the DDL.
    - **The drift gate is what keeps #1823 fixed**: `scripts/assert-schema-drift.mjs` in all four server apps (`npm run test:schema-drift`; adapted from authup) wraps typeorm-extension's `assertSchemaMatchesMetadata` with `skipWithoutMigrations: true` and catches only `SchemaDriftError`, and `tests-migrations` runs it as a new step after the idempotency replay. The migration chain and the entity metadata are two independent descriptions of one schema, and nothing compared them before — the suites `synchronize()` from the entities. authup's populated round-trip (`verify-latest-migration.mjs`) was deliberately NOT ported: it boots the real app for seeding, which needs per-service infrastructure the migration job lacks (Authup at minimum — the job provides databases only). It round-trips only the NEWEST migration, so the telemetry IPv6-lossy `down()` deeper in the chain is no obstacle — recorded as an open follow-up in [testing.md](.agents/testing.md#migration-tests).

26. Messaging delivery semantics (plan 018, phase 1) — Implemented. Fixes only the defects that have local fixes; the topology/orchestration findings stay open. What is not obvious from the diff:

    - **A WORK message used to get exactly one attempt.** The AMQP driver acked and skipped every `redelivered` message, so a handler throw (nack + requeue) or a worker crash mid-build lost the command silently. A failure or redelivery now re-publishes with `metadata.attempt + 1` and exponential backoff (`maxAttempts` 5, `retryDelay` 1s, capped at 30s), then drops with an error log. Deliberately no dead-letter queue yet. A redelivery is NOT always a dead consumer: a channel reset (reconnect) redelivers a message whose handler is still running in a live process, so the driver tracks in-flight ids and skips such a copy. That guard is per process only — a redelivery landing on ANOTHER replica (connection drop, `consumer_timeout`) still runs a second time until a distributed claim exists (F9/F10). Operator consequence: RabbitMQ's `consumer_timeout` must exceed the longest build — documented in [deployment configuration](docs/src/guide/deployment/configuration.md#message-delivery-rabbitmq).
    - **`context.handle` neither awaited nor returned the child handle**, so every `await context.handle(EVENT)` resolved immediately: a command was acked before its result event was published, and a publish error became an unhandled rejection. It now returns the promise, so awaited publish failures reach the handler's `catch` (and the driver's retry). Not covered: the `EXECUTION_PROGRESS` callbacks run by docken's `waitForStream`, which invokes `onBuilding`/`onPushing` fire-and-forget — a failed progress publish there was and still is an unhandled rejection, and those publishes are not ordered against `EXECUTION_FINISHED`.
    - **All consumers run at `prefetchCount: 1`, events included.** Aggregator handlers read-modify-write the entity, and typeorm's `save()` diffs against the database, so a concurrently handled `PROGRESS` wrote `STARTED` back over `EXECUTED`. Serialization holds per replica only. Across replicas, `isProcessStatusTerminal` (`core/services/helpers.ts`) makes `STARTED`/`PROGRESS` no-ops once a process is terminal; only the command path (`STARTING`) leaves a terminal status. `MasterImageService` BUILD now saves `STARTING` **before** dispatching, for the same reason.
    - Failure payloads typed `error: Error` serialized to `{}`: `serializeMessageBusPayload` (server-kit; now hubwire's `serializeMessage`) keeps `name`/`message`/`code` on the wire. A failed master-image build emitted `EXECUTION_FINISHED` — it now rethrows into `EXECUTION_FAILED`. The synchronizer's `'*'` telemetry handler was shadowed for `EXECUTION_FINISHED` (a specific handler wins), so that handler now records the event itself. `'*'` stays a fallback, not a tap. The AMQP driver and `RegistryProjectLinkHandler` now receive a logger, and a dispatch that no consumer accepts (memory driver) logs a warning — the AMQP driver's `publish()` now resolves `true` once confirmed, since amqplib's boolean only reports write-buffer backpressure. Retrying WORK queues include the shared telemetry log queue, where the backoff holds the single prefetch slot; the log writer therefore drops a line that fails validation **or that the log store rejects** (a VictoriaLogs outage) instead of letting it be retried — a retry would hold the slot through its backoff and pile every service's log lines up in the broker.

    **F4 landed on amqp-extension 5**: the six reply routings (worker builder/distributor/master-image events, storage bucket/bucket-file events) are WORK queues with `ordered: true`, which the AMQP driver declares as `x-single-active-consumer` on **both** publish and consume (the broker answers differing arguments with 406). Ordering is load-bearing, not cosmetic: plain competing consumers would let a stale `PROGRESS` save overwrite `EXECUTED` on another replica. An ordered redelivery whose original still runs in-process is held until the original settles rather than acked, since acking frees the prefetch slot and lets the next message of the stream run beside it. A retry re-publishes to the queue tail, so a retried event can land after a later one — `isProcessStatusTerminal` absorbs that for status events. Rollout: worker and storage before server-core. v5 declares every default-exchange queue with `x-queue-type: classic`; verified against RabbitMQ 4 that this re-declares v4's argument-less queues in both directions without a 406.

    **Race-safe status transitions (F9, #1937, plan 009 phase 1).** Every process-status transition — analysis build/distribution start, configuration lock/unlock, master-image BUILD and its dispatch-failure rollback, and the three worker aggregators — runs read-check-mutate-save on a row held by `SELECT … FOR UPDATE`, via `updateLockedEntity` (`adapters/database/locked-update.ts`), exposed to `core/` as `IAnalysisRepository` / `IMasterImageRepository` `.updateLocked(id, fn)`. So `canStart` and `isProcessStatusTerminal` are evaluated on the row as it is now: of concurrent starts exactly one dispatches, and a late event cannot write an older status back. Every other writer of those rows goes through the lock too, or a stale copy is written back (`save()` diffs against the database): the three metadata recalculators apply only their derived fields to the locked row (`saveAnalysisPatch`), `AnalysisService.update` (a user PATCH, which awaits a permission evaluation between its read and its write) and the master-image synchronizer `Object.assign` their fields into it. Not `repository.merge()` inside the callback: typeorm's mutates, the test fake's returns a copy, so the port does not promise either. Deliberately **not** `repository.update()` — it bypasses the subscribers that publish the realtime + audit events. The callback is synchronous (nothing awaited under the lock); dispatch happens after commit. A master-image BUILD claims `STARTING` only from a non-`STARTING` row (400 otherwise), so its dispatch-failure rollback, which reverts only a row still `STARTING`, can only undo its own claim. A `STARTING` older than 15 min is presumed dead and may be taken over — master images have no check command, so this stays their only escape — the reconciler (F14) covers analyses only. A CHECK_FINISHED verdict carries `checkedAt` (the snapshot's `updatedAt`) and is dropped when the locked row is newer; a verdict without it (older worker) applies as before. Any write bumps `updatedAt` — a node-progress recalc included — so a verdict that raced an unrelated write is dropped as well, silently; re-run the check. better-sqlite3 runs unlocked and is **not** race safe (no row locks; its one shared runner nests concurrent transactions as savepoints) — no worse than the plain `save()` it replaced. Pinned by `test/unit/adapters/database/status-transition-lock.spec.ts` (concurrent starts, and a late `EXECUTION_PROGRESS` read while `EXECUTED` commits for each of the three aggregators), negative-controlled on postgres and mysql. Not done: run ids to drop a previous run's late `EXECUTION_FINISHED` after a new `STARTING`. Since then the aggregators no longer touch the `DataSource`: the status rules moved into core (`applyEvent` on `AnalysisBuilder` / `AnalysisDistributor` / `MasterImageBuilderService`), the storage-bucket and authup handlers go through the repository ports, and `updateLockedEntity` is called only by the repository adapters — an authup user deletion now detaches analyses via `updateLocked` instead of a full-copy save.

    **TaskManager removed (F10/F11).** Its only job was correlating storage bucket replies, and the reply already names its analysis bucket: `CREATION_FINISHED` is linked by `refType: 'analysis'` + `refId` + `parseAnalysisBucketName(name)` (core-kit, the inverse of `buildAnalysisBucketName`), and a reply that does not resolve to one is ignored. A reply for an `(analysisId, type)` already linked to a different bucket — a repeated `check()` sent a second create — dispatches a storage delete for that new orphan bucket, never for the linked one; the ordered reply queue (F4) makes this check-then-link race-free without a lock. `DELETION_FINISHED` matches by bucket id only, as before. `CREATION_FAILED` is now consumed and logged against the analysis — storage echoes the command's optional `refType`/`refId`/`name` on it, and without them (older storage) the error is logged without refs; nothing is persisted and the F14 reconciler does **not** re-provision it — a missing bucket still needs a `storageCheck` (open). **Breaking:** `TaskManager` (and its types) is removed from `@privateaim/server-kit`; `IBucketCaller` takes no metadata. **Rollout:** stop old server-core replicas before new ones serve traffic — an old replica holding the `storageBucketEvents` slot drops `CREATION_FINISHED` for a create a new replica sent (no task entry), leaving that analysis bucket-less until a `storageCheck` command; the reverse direction links fine. See [deployment configuration](docs/src/guide/deployment/configuration.md#message-delivery-rabbitmq).

    **Reconciler + staleness in core (F13/F14).** The 15-min stale verdict moved from the worker check handlers into core: a worker now reports an in-progress (`STARTING`/`STARTED`) process as-is, and `applyEvent` CHECK_FINISHED turns that into `FAILED` when the locked row's `updatedAt` is older than `ANALYSIS_PROCESS_STALE_THRESHOLD_MS` (`core/services/helpers.ts`). `AnalysisReconciler` (`core/services/analysis-reconciler/`) runs from a `ComponentsModule` background component (`app/components/analysis-reconciler/`, node-client shape: a pass at start, then every 5 min) and dispatches the existing build/distribution check for every in-progress row older than the threshold (`IAnalysisRepository.findManyInProgressUpdatedBefore`, a `Raw` bound `Date` — the timestamp-filter trap). No lock: per replica, duplicate verdicts are dropped by `isCheckVerdictStale`. So a long single step is not judged stale, the builder/distributor execute handlers send a heartbeat `EXECUTION_PROGRESS` (last percent) every 5 min, and core's PROGRESS branch stamps `updatedAt` explicitly when the percent is unchanged (typeorm writes an explicit update-date value instead of `CURRENT_TIMESTAMP`; pinned on postgres/mysql/sqlite by `test/unit/adapters/database/process-staleness.spec.ts`, negative-controlled) — throttled to once per `ANALYSIS_PROCESS_HEARTBEAT_STAMP_MS` (1 min), otherwise the event is a no-op with no save. The heartbeat goes quiet after 2 h without real progress, so a hung docker stream goes stale — but stale is not recovered by itself: with one worker the CHECK waits behind the hung EXECUTE on the same prefetch-1 queue, so it takes a worker restart, a second worker replica, or RabbitMQ's `consumer_timeout`. Ceilings: a CHECK per stuck row per replica per 5 min with no TTL — they pile up while no worker consumes; master images and failed storage buckets are not reconciled. **Rollout: workers before server-core** — an old worker still applies its own 15-min rule and sends no heartbeat, so the new reconciler's automatic check would fail its healthy long builds.

    - **One contract for two things that were both called "component".** `IComponent { start, stop, status }` (hubwire) now covers the message-handler router (`Component`, formerly `BaseComponent`) and the scheduled background job (`defineScheduledComponent({ schedule, run, runOnStart?, hooks? })`). Every hand-written `task`/`stopped`/`lastSuccessAt`/`runningSince` block is gone: node-client sync and the analysis reconciler (server-core), the telemetry event cleaner, the messenger sweeper. A `run` that throws is logged and does not stamp `lastSuccessAt`; node-client and the reconciler throw after logging a partial failure (`failed > 0`) for that reason, and pass **no** hooks to the scheduled component so a failure is logged once, at error level (the cleaner and sweeper pass `createScheduledComponentLogHooks`, so theirs log at warn). `start()` never rejects.

Before, a consumer had no `stop()` (the bus could not cancel one), the telemetry cleaner's cron task was never stopped, and the AMQP connection outlived the app. server-core starts its components fire-and-forget, so its teardown awaited those starts first — a synergos worker caller still starting would otherwise subscribe after its `stop()` (dropped in item 35: hubwire's `RemoteWorker.stop()` waits for a concurrent start). Ceiling: a scheduled component's `stop()` does not wait for a pass already running.
    - **The telemetry cleaner is no longer a command.** `EventComponentCleanerHandler` became `createEventCleanerComponent` (`app/components/event-cleaner/`, `'0 1 * * *'` plus a pass at start). Its first pass used to run inside `Component.initialize()`, where a failure could reject boot; now it is logged and boot continues. The messenger sweeper uses `runOnStart: false`, keeping "first sweep one interval after boot"; the unref'd `setInterval` is gone, so `teardown()` is what lets the process exit.
    - **F17 — registry dispatch follows #1962** (the in-process fallback is gone since item 35). `RegistryComponentCaller` publishes each command to `registryCommands` itself (`buildMessage` + `IMessageBus.publish`, the same message a `DispatchCaller` builds) because synergos's `DispatchCaller.call()` did not report whether the bus accepted it. Accepted → done: the registry consumer on whichever replica takes it runs it, with the bus's retry. Not accepted (memory driver with no consumer yet) → `onUndelivered` (warn) and the command runs in-process through a `DirectCaller`; no bus → in-process. A failing direct call surfaces its own error and is not re-queued. The compound caller (in-process first, then the queue, every error swallowed) is gone and was not ported to hubwire. `registryCommands` is not `ordered`, so a registry-project rename sends one `PROJECT_RELINK` (carrying the old `externalName`) instead of an unlink and a link; an admin's separate `PROJECT_UNLINK` / `PROJECT_LINK` requests can still race (making the routing `ordered` would answer 406 until the existing queue is deleted).
    - **F6's last-attempt detection needed synergos ≥ 0.1.0** (0.2 reads `metadata.delivery` instead, item 35). #1962's `isRetryableFailure` (`apps/server-core-worker/src/app/components/helpers.ts`) reads `metadata.attempt` and compares it with `MESSAGE_BUS_MAX_ATTEMPTS`, which `MessageBusModule` also passes as the AMQP driver's `maxAttempts`, so the two cannot diverge. With amqp-extension the counter travels only in the `x-attempt` header; `@synergos/amqp` 0.1.0 copied it into `metadata.attempt` on consume (tada5hi/hubwire#11) — never onto the wire. On 0.0.0 the attempt always read 1, so a transient failure was retried and then dropped instead of reported as `*_FAILED`.
    - **Wire format is byte-identical except one field: the retry counter moved from the body (`metadata.attempt`) to the `x-attempt` AMQP header**, set by amqp-extension's `retry` consume option (`maxAttempts` 5, base delay 1s doubled per attempt, capped at 30s — unchanged). Exchange names (`FLAME` is now `MESSAGE_BUS_TOPIC_EXCHANGE` in server-kit), `type`/`messageId`/`persistent`, `x-single-active-consumer` on ordered routings and `prefetchCount: 1` are unchanged. **Mixed versions during a rollout retry more, never less, and never forever:** a missing or invalid header reads as attempt 1, an old driver re-publishes without headers (resetting the new side's count) but keeps counting in the body, which the new side never rewrites — so the old side's body counter still bounds a message that bounces between old and new replicas. No upgrade order is required for this; the item-26 orders (workers and storage before server-core) still hold. The in-process redelivery guard now lives in amqp-extension (per consumer, kept across reconnects; still per process — F9/F10 unchanged): a redelivered copy of a message whose handler still runs is held until the original settles, ordered or not, then acked — or requeued when the original's retry re-publish failed, since the original's nack went to the reset channel (hub's driver acked the copy and lost the message then). A retry logs a warning and an exhausted message an error naming its type and id; a crashed redelivery's retries are not logged (amqp-extension reports only its drop). A worker reply never carries the command's body `metadata.attempt`, so an old server-core does not drop it early.

The 0.1 imports (the library's former package name) became `hubwire@^0.2.1` / `@hubwire/amqp@^0.2.1` (`@hubwire/test@^0.1.1` as a dev dependency of server-kit and server-core); callers became dispatchers and workers: `DispatchCaller` → `RemoteDispatcher`, `DirectCaller` → `LocalDispatcher` (`callAndWait` → `dispatch(...).replies`, `callWith` → `component.handle(..., { handle })`), `WorkerCaller` → `RemoteWorker` (`consumeRouting` / `publishRouting` → `consume` / `publish`). What is not obvious from the diff:
    - **Breaking for npm consumers of the kits.** The hub caller subclasses extend `RemoteDispatcher` and are renamed `*Caller` → `*Dispatcher` with `call*` → `dispatch*` methods, no aliases (`AnalysisBuilderComponentCaller` → `AnalysisBuilderComponentDispatcher` with `dispatchExecute` / `dispatchCheck`, `BucketComponentDispatcher`, `BucketFileTaskDispatcher`, `BucketFileEventDispatcher`, `LogComponentDispatcher.dispatchWrite`, `EventComponentDispatcher.dispatchCreate`, `MasterImage*ComponentDispatcher`, …): their options lost `hooks`, and the inherited `call()` is now `dispatch()`. server-telemetry-kit's `EntityEventHandler` context key `eventComponentCaller` → `eventComponentDispatcher`, its port `IEventPublisher.callCreate` → `dispatchCreate`.     - **`publish()` no longer reports delivery.** It resolves `void` once the transport took the message, and a WORK queue keeps a message until a consumer takes it — the memory driver too. So `RegistryComponentDispatcher`'s (formerly `RegistryComponentCaller`) "accepted nowhere → run in-process" fallback (F17) is gone: with a bus it only dispatches (`RemoteDispatcher`), without one it runs the component through a `LocalDispatcher`. A command dispatched before the registry consumer started now waits in the queue instead of running inside the request.
    - **The last attempt comes from the driver.** `isRetryableFailure` reads `metadata.delivery = { attempt, maxAttempts }` instead of comparing `metadata.attempt` with `MESSAGE_BUS_MAX_ATTEMPTS`; `MessageBusModule` still passes that constant as the AMQP driver's `maxAttempts`. Without a delivery (an in-process call) or on the memory driver (`1/1`) nothing retries, so a transient failure is reported as `*_FAILED` instead of rethrown into a drop.
    - **Shutdown waits for a scheduled pass.** `stop()` never waits for a cron pass in flight; server-core's `ComponentsModule`, telemetry's `ComponentsModule` and messenger's `SweeperModule` now `stop()` every component, then await `settled?.()` on each (hubwire 0.2.1: optional on `IComponent`, required on `IScheduledComponent`), so a pass cannot outlive the database; scheduled components share the one `IComponent[]` with the workers. `MessageBusModule.teardown()` closes the bus (`IMessageBus.close()`) rather than the driver.
    - **Cross-service publishes need AMQP.** A memory WORK queue keeps every message until a consumer takes it (0.1 dropped it), and without `AMQP_URL` no service but telemetry consumes the log and entity-event queues — so every log line and entity event would stay in the heap until `close()`. `MessageBusModule` therefore also registers the bus as `RemoteMessageBusInjectionKey`, only when the driver is not the memory driver, and the publishers whose consumer is another service resolve that token and are not built without it: the factories' log transport `save` and `EntityEventHandler` (server-core, server-storage; server-telemetry consumes its own), server-core-worker's analysis log lines, server-storage's bucket and file events to server-core. Pinned by server-kit's `message-bus-module.spec.ts`. Ceiling: server-core's commands to the worker and to storage (build, distribute, bucket and file tasks) still use the always-registered bus, so without AMQP a triggered command waits in the memory queue until shutdown.
    - **No start/teardown handshake.** server-core's `ComponentsModule` and `AggregatorsModule` start fire-and-forget and `teardown()` only `stop()`s (then `settled?.()`): a `RemoteWorker.stop()` waits for its own start and leaves no consumer, `settled()` covers a scheduled component's first pass, and the authup aggregator attaches its listener before it subscribes, so a `stop()` mid-start removes it.
    - **Tests wait for handlers, not for `publish()`.** Bus-backed specs `drain()` (`@hubwire/test`) before asserting; the hooks spec asserts a failing handler through `onError` instead of a rejected publish; the storage-bucket-file spec's never-delivering bus is `FakeMessageBus`.
