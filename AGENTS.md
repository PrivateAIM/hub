# FLAME Hub — Agent Guide

FLAME Hub is a monorepo for the central services of the FLAME platform — a privacy-preserving analytics infrastructure. It contains backend services (core API, storage, telemetry, messenger, worker), a Nuxt frontend, shared libraries, and a VitePress documentation site. All packages are TypeScript, built with tsdown (libraries) or tsdown + tsc (services), orchestrated by Nx.

## Quick Reference

```bash
# Setup
npm ci

# Development
npm run build                   # Build all packages (Nx)
npm run test                    # Test all packages (Nx + Vitest)
npm run lint                    # ESLint across all packages
npm run lint:fix                # ESLint with auto-fix

# Dev servers
npm run dev --workspace=apps/client-ui          # Nuxt frontend
npm run dev --workspace=apps/server-core        # Core API server
npm run dev --workspace=apps/server-messenger   # Realtime/WebSocket server
npm run dev --workspace=apps/server-core-worker # Worker service
npm run dev --workspace=docs                    # Documentation site
```

- **Node.js**: 24
- **Package manager**: npm (workspaces)
- **Build orchestration**: Nx 22

### Workspace Layout

Applications (services + frontend) are in `apps/`, shared libraries are in `packages/`, and documentation is in `docs/`. Libraries export ESM (`dist/index.mjs` + types), services compile with tsdown + tsc.

## Documentation

The `docs/` directory contains a VitePress documentation site. When making changes that affect user-facing behavior, configuration, APIs, or service architecture, **update the corresponding docs pages**. The docs site is the authoritative reference for Hub — docs.privateaim.net should link here, not the other way around.

Key docs areas to keep in sync:
- `docs/src/reference/<service>/` — per-service pages (env vars, endpoints, usage)

Four things in it are not version-string churn:

    - **The issue model moved from validup to `@ebec/core`** (port of [authup f9db4e1a](https://github.com/authup/authup/commit/f9db4e1a740292b1d1ca178c3a5764fadaf84d0f)). validup 2.0 dropped the re-export, so `Issue` / `defineIssueItem` now come from `@ebec/core` while the validator engine (`Container`, `ValidupError`, `isValidupError`, `stringifyPath`, …) stays on validup. `HubError` no longer declares its own `issues` — it inherits `readonly issues: ReadonlyArray<Issue>` from `BaseError`, populated from constructor options, so `sanitizeError` passes validup issues in rather than `push`ing them after construction. `packages/errors` dropped its validup dependency entirely.

Restoring the old guard fails 7 of the 8 specs in `packages/server-http-kit/test/unit/sanitize-error.spec.ts`, four of which predate this change. The guard now reads the `@instanceof` chain only, via `matchesInstanceof`, which also matches the JSON-serialized form — so a hub error survives a hop between services. `HubError.toJSON()` re-appends the chain after spreading `data`, since `data` is an open bag that could otherwise overwrite the one key the guard reads.

All 16 entity schemas, the client query build inputs and `ListMeta` moved; `createList` reads both spellings (definedness, not key presence) because client-vue is published and a consumer may still spell it `sort`. **The URL parameter is unchanged — a query string still carries `?sort=-updatedAt`.** rapiq 2.1 also added schema index declarations, so descriptions gained `indexes`, `filters.caseSensitive`, `filters.indexed` and `sorts.indexed` (all `null`/`false` — no hub schema declares `indexes` yet). Docs updated in `docs/src/guide/development/api.md` and `docs/src/reference/{core/core-http-kit,storage/storage-kit}.md`.

    - **The rapiq parse trace is forwarded into the HTTP error payload**, and that is a fix, not a nicety. rapiq 2.2 collects every violation and raises one aggregate whose message is a bare count (`The input was rejected: 1 violation.`), so a rejected query used to answer 400 naming nothing. `sanitizeError` now passes `ParseError.issues` through — unmapped, because `@ebec/core` 1.3.2 vendored blemish's issue model verbatim and the two `Issue` types are mutually assignable. The rapiq branch had to move **above** the validup branch: `isValidupError` also falls back to a shape check (any `Error` with a non-empty well-formed `issues` array), so with @ebec/core 1.3.2 it now swallows traced rapiq errors — the same inversion `isHubError` had to be narrowed for, one library up. Error-payload shape documented in [api.md](../docs/src/guide/development/api.md#error-responses).

Note a rejected query still yields **one** issue rather than one per bad key: the expression dialect throws structurally on the first disallowed filter key and ends the parse, while the other parameters run in rapiq's default drop mode. 21. SSR hydration handoff (#1805) — Implemented (what the server render fetched now reaches the browser instead of being discarded). client-ui runs `ssr: true`, but every detail page fetched its record **twice**, and a list's initial load ran in a detached microtask that resolved *after* the HTML was flushed — the server paid for the request and shipped an empty list anyway. The seam is `@authup/client-web-kit`'s hydration store, provided by `@authup/client-web-nuxt`'s kit plugin over `nuxtApp.payload.data` (both already dependencies at beta.63 — **no authup bump**). Hub adds **no install option and no plugin**: `createListRaw` calls `injectHydrationStore()` and no-ops when it returns `undefined`, so a host without one skips the server-side load entirely rather than rendering rows the hydrating client cannot reproduce. Four things in it are not obvious:

    - **The list key is `flame:list:<type>:${useId()}`, never the query.** A query-derived key has to be re-derived *identically* on the client, which makes filter insertion order, a `query` prop assembled from store state that is not populated yet on one side, and two same-query lists on one page all load-bearing — and each of those fails **silently**, as a list that simply fetches twice again. Vue 3.5's `useId` is stable per component-tree position across the boundary, so agreement is structural rather than something a caller can get wrong. The entity type is in the key only to bound the blast radius of an entry that is recorded but never adopted.
    - **`onServerPrefetch` is registered on BOTH sides, and that is load-bearing.** A non-empty `instance.sp` is what makes Vue call `markAsyncBoundary()` after setup, giving the component's subtree a fresh `useId` counter; `instance.sp` is read in exactly two places (`runtime-core`'s boundary check and `@vue/server-renderer`, the only invoker). Registering the hook only under `isServerRuntime()` marks the boundary only on the server, so every `useId()` inside or after a list shifts between renders — a second same-type list then derives the key the server used for the FIRST one and adopts the wrong rows, with its own load suppressed so it never corrects. `list-hydration.spec.ts`'s two-list round trip is the negative control; it fails the moment the registration is moved back inside the server branch.
    - **The composed `query` travels in the snapshot.** `query` is assigned nowhere but inside `load()`, which the adopting client skips, and the socket handler reads its sorts to decide whether a realtime-created entity belongs at the top of a full first page. Without it, realtime inserts stop silently on every hydrated list (a ≥10-row list on `/projects`, `/projects/in`, `/admin/nodes`, …) until the user pages or searches.
    - **A collection query must not request a permission-gated column any more.** The list's rows now reach the payload, i.e. the served HTML document. `fields: ['+accountSecret']` was dropped from the registry-projects list: nothing there rendered it (the details modal re-resolves by id with its own `+accountSecret`), so it was pure over-fetch that would have put every Harbor robot secret into the document.
    - **Only a load that ran to completion may be recorded.** An adopted snapshot *suppresses* the client's own load, so recording what a failed — or coalesced-away — load left behind strands the list on it with no retry. The `loaded` flag set at the end of `load()`'s try block is the enforcement point: `onServerPrefetch` awaits `load()` in a try/catch and records nothing unless it is set. `onServerPrefetch` is also what makes the renderer **wait**, which puts a list's upstream latency on the SSR critical path — the nine `[id].vue` detail pages already blocked SSR by awaiting in `setup()`, so this is not a new class of dependency.
    - **`useAsyncData` needs `deep: true`.** Nuxt 4 returns a `shallowRef`, and every one of the nine pages mutates its entity **per property** (`updateObjectProperties` does `src.value[key] = …`, or `extendObject`), so without it the page silently stops updating after a save. `useEntityRecord` centralises it. A second Nuxt trap sits next to it: 4.5.2's `asyncData.js` **defers** `initialFetch` to `onBeforeMount` during hydration when the payload holds no entry for the key, so `await useAsyncData(...)` can resolve with `data.value === undefined` **and** `error.value === null` — a guard of the form `if (error.value || !data.value) redirect` therefore bounces a page that is merely late.
    - **No authenticated route may get an `swr` or `isr` route rule** — the payload is per-request, and a cached one would be served to the wrong session. `apps/client-ui/nuxt.config.ts` declares exactly one route rule, `'/login/callback': { ssr: false }`.

    One consequence is accepted rather than fixed: list rows now render on the server, which puts `<VCTimeago>` on both sides of the boundary for the first time. It computes a relative string during `setup()`, so a bucket crossing between render and hydration — or clock skew — is a text mismatch, and Vue `console.error`s those in production builds too. Vue repairs the text; the cost is console noise on list pages and one more thing to rule out when debugging a real mismatch. The fix belongs upstream in `@vuecs/timeago` (SSR-stable first render, relative string in `onMounted`).
