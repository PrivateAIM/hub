Storage (server-storage) ​

The Storage service manages file and object storage, backed by MinIO (S3-compatible) or, without a MinIO connection, the local filesystem. It provides bucket and file CRUD operations with streaming support.

Running ​

bash
# From the repo root: build every workspace, then start the HTTP server
npm run build
npm run cli --workspace=apps/server-storage -- start

# Database migrations: run | revert | status | generate
npm run cli --workspace=apps/server-storage -- migration run

# Docker
docker run -e ... ghcr.io/privateaim/hub storage cli start

start creates the database when it does not exist and applies pending migrations before it serves.

Dependencies ​

  • Database — MySQL, PostgreSQL, or SQLite
  • Authup — OAuth2 identity provider
  • MinIO (optional) — S3-compatible object storage; without it files go to the local filesystem (STORAGE_PATH), which several replicas do not share and a container loses unless the path is a volume
  • RabbitMQ (optional) — AMQP message bus; without it no analysis bucket is created, because server-core sends bucket commands over the bus
  • Redis (optional) — realtime entity events

Port is required, nothing may follow it (no trailing /), and key and secret may contain only letters, digits and _. A malformed value stops the start (Invalid MINIO_CONNECTION_STRING format.).

A token another client exchanged is refused (401). A name is looked up once through Authup, which needs client_read for storage's own client; an id needs no lookup.

A bucket with a refType and refId is unique per (refType, refId, name). Only the service owning the referenced resource sets a refId, through the create bus command; POST /buckets with a refId answers 400, since storage cannot check who owns the referenced resource. A repeated bus create of a triple that already exists in the same realm answers with the existing bucket instead of a second one; the same triple in another realm fails. Buckets without a ref are not deduplicated: they may share a name.

A bucket records its creator (actorId/actorType): for POST /buckets the authenticated identity (an actor in the body is ignored), for a bus create the actor named in the command. The creator may update, clear and delete the bucket, and delete its files, without bucket_update/bucket_delete; everyone else needs the permission and realm access. Buckets without a recorded creator are not backfilled, so only permission holders can manage them.

Uploading (POST /buckets/:id/upload) into a bucket without a refId requires being its creator, or bucket_update with realm access; anyone else gets 403 before a file is stored. A bucket with a refId (e.g. an analysis bucket) accepts uploads from any authenticated caller, because its legitimate uploaders span realms and storage cannot evaluate the referencing service's permissions: the owning service checks each upload when it registers it (see Writing analysis buckets and files).

Capability Tokens ​

Besides a login, server-storage accepts an Authup capability token (kind: capability_token, audience storage) minted by server-core through POST /analyses/:id/storage/token. It is verified locally (signature against Authup's /jwks, aud, kind, exp) and grants only the actions on the resources in its cap claim. Only a token exchanged by CAPABILITY_CLIENT_ID (its act.sub) is accepted, as Authup lets every client with a storage exchange capability mint one. A capability request carries no identity: every route not listed below answers it 401.

WhereRoutes
Authorization: Bearer headerGET /buckets, GET /buckets/:id, POST /buckets/:id/upload, GET /bucket-files, GET /bucket-files/:id, DELETE /bucket-files/:id
?dt=<token> query parameterGET /buckets/:id/stream, GET /bucket-files/:id/stream only, and only for a token living at most 60 s (exp - iat)

Bucket create, update, delete and clear are login only. A token in the query is never accepted on any other route, and a query token that lives longer than 60 s is refused (401). Only one dt is allowed.

cap entries are type:id:actions:

EntryCovers
bucket:<id>:readThe bucket, its tar stream and every file in it
bucket:<id>:writeUploads into the bucket
bucket:<id>:deleteDeleting files of the bucket
bucketFile:<id>:read / :deleteThat one file only

Listings are narrowed to the covered buckets and files: a filter on another bucket returns nothing. Stream responses send Referrer-Policy: no-referrer so a token in the URL does not leak, and the query string is never logged. server-core remains the authority on who may upload (it judges each file when it registers it).

Response Shapes ​

Every bucket and bucket-file endpoint answers with a { data, meta } envelope — the record (or the record array) under data. Query-capable GETs advertise the endpoint's queryable vocabulary at meta.schema; mutations carry meta: {}.

Three surfaces stay outside the record envelope:

EndpointShape
GET /{ version, timestamp } — service metadata, flat
GET /buckets/:id/stream, GET /bucket-files/:id/streamflat binary streams with attachment headers
POST /buckets/:id/uploada collection ({ data: files, meta: { total } }), because it uploads many files — no schema

See API Reference for the full contract and the meta.schema reading rules.

Architecture ​

  • BucketEntity / BucketFileEntity — TypeORM entities tracking storage metadata
  • StorageModule — registers the storage adapter in the DI container: a MinIO client when MINIO_CONNECTION_STRING is set, else the filesystem adapter on STORAGE_PATH
  • BucketComponent — AMQP consumer for asynchronous bucket operations: create, delete and clear (removes every object and bucket-file row but keeps the bucket, emitting clearingStarted / clearingFinished / clearingFailed)
  • Subscribers — publish domain events on bucket/file changes
